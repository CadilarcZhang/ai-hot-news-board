# 第一次百度搜索为什么慢

预览函数在 `iad1`。2026-11-01 对现网部署 `dpl_o1HEht1Hz3jPz88wEcvP5szutES3` 的测量：

- 百度结果日志大约在请求开始后 **2.7s**（含一次失败的 Google Custom Search）。
- 客户端要到 **15s 左右** 才收到第一条 `sources`。这段时间花在正文抓取，不是花在百度检索本身。

`generate-with-search` 以前把 `sources` 放在全部正文抓完之后。Google 开关打开时走 `fetchMultipleArticlesWithRetry`：每批最多 2 篇、批间等待 1.5s、正文太短还会按 1s/2s 再下两次同一页面。百科类页面经常是空正文，有用的第三条要等前面的重试结束才开始。

## 这次改了什么

选择器和「Google 有结果就用 Google，否则用百度」没有改。响应里的 `sources` 仍是 `{ title, link }`。

- Google 与百度同时发出。Google 先返回非空结果就用 Google，并中止百度。百度先拿到结果就立刻返回，不再等 Google 的 5 秒超时。百度超时 7s。连接重置仍立刻再试一次，读超时不重试。两条相同的百度请求只抢响应头：先拿到头的那条继续读正文，另一条马上取消，不并行下两份页面。页头 script/style 先剥掉，原来的选择器解析出第一条就写 `sources`，凑满 5 条再停止下载。缓存回放同样先写非空 `sources`，并带上 4KB 填充，避免命中缓存时把链接丢掉或憋在缓冲里。

## 2026-11-01 复测：军报冷请求 4.7s

同一预览部署上，`军报：广大官兵坚决拥护党中央决定` 的函数日志是 `region=sin1`，`百度搜索耗时 3568ms`，搜索阶段 3570ms。客户端 first sources 4.706s。同一次验收里画地为牢、国防部请求落在 `hkg1`，另一条 generate 落在 `hnd1`。Fluid 没有把函数留在 iad1。iad1 上其他标题的百度检索大约 1.3–2.3s。

因此 `vercel.json` 的 `regions` 固定为 `iad1`（不是 hkg1/icn1/sin1）。这只约束这个部署的函数跑在 iad1。进程启动时预解析 `www.baidu.com` 的 IPv4 并做一次 TLS 预热，供第一次检索复用。

## 2026-11-01 VIVANT 冷请求 3.0s

`国防部批日剧VIVANT` 在 `dpl_9mHBByen8UTobSuSjRjRNpjyngXx` 上的函数日志是百度 2052ms、headers 1471ms、bytes 393216、hedge 0，搜索阶段同样 2052ms。客户端 first sources 3.045s。同页的军报 1.172s、画地为牢 1.168s 总时长只有约 2s，是内容缓存回放，不是冷检索。慢的那次是首包本身偏慢，再加上结果要读到页面后部才被选择器看到。

- 出站 Agent 改为 IPv4 + `keepAlive`，同一实例复用连接。
- 搜到结果后立刻写 `sources`，再并行抓最多 5 条候选（搜索本来就返回 5 条；旧的两两分批会误抓到第 4 条，可用正文经常在那里）。成功正文仍最多保留 3 篇。凑够正文后中止还在挂起的请求，不再空等 8 秒超时。正文太短不再对同一 URL 空等重试。抓完若可用来源和先发出的列表不同，再写一次 `sources`，前端会换成真正读到正文的链接。
